# Design Decisions

## State isolation: separate state files per environment

Terraform workspaces were considered but rejected for the dev/prod split in
this project, for two reasons:

1. **Shared credentials.** Workspaces share the same provider block and
   backend, meaning whichever Service Principal runs Terraform typically has
   RBAC access to every workspace. Separate environment folders let dev and
   prod use independently-scoped credentials, so a leaked dev credential
   can't touch prod.
2. **Code cleanliness.** Workspaces push environment differences into
   `terraform.workspace == "x" ? ... : ...` conditionals scattered through
   shared code. Separate environment folders keep environment-specific
   values (VM size, DB SKU, CIDR ranges) in each environment's own
   `variables.tf`, with the actual resource logic staying identical and
   shared via modules.

## Secrets: Key Vault + random_password, never in .tfvars

The database admin password is generated by Terraform's `random_password`
resource and written directly into Key Vault as a secret. It is never set as
a plain variable value, never appears in a `.tfvars` file, and the module
output that exposes it is marked `sensitive = true` so it won't print in
Jenkins console logs or `terraform plan`/`apply` output.

Trade-off worth stating out loud in an interview: the password still lands
in the Terraform **state file** in plaintext, because Terraform must record
the resolved value of any attribute it sets on a resource (the Postgres
server's `administrator_password`). This is unavoidable when Terraform
itself is the one creating the resource that needs the password — the
mitigation is treating state itself as sensitive (encrypted backend, access
restricted), not pretending the password never touches state at all.

## Why a manual approval gate in Jenkins, not just automated apply

`plan` runs automatically on every pipeline execution so the diff is always
visible before anything changes. `apply` and `destroy`, however, pause on an
`input` step requiring a human to click "Proceed." This mirrors how most
real infrastructure teams operate: full automation up to the point of
irreversible/costly action, with a deliberate human checkpoint before that
action executes — especially for `prod` and for any `destroy`.
